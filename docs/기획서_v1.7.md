# 알밥 — 알고 먹이는 밥그릇

**v1.7 · MVP 기획서 (업데이트)**
반려동물 사료 성분 등록·검색 서비스

> v1.6 대비 변경사항: 6~7단계 실제 구현 중 발견한 사항 반영 — 브랜드 영문/한글 표기 별칭 매핑을 차후 업데이트 항목으로 추가

---

## 1. 서비스 개요

**문제의식**: 사람들이 반려동물 사료를 고를 때 성분을 보고 싶어하지만, 대부분 출처 불분명한 "떠도는 리스트"에 의존하고 있음

**해결 방향**: 화해(성분 분석 앱) 모델을 참고해, 사용자가 직접 사료 성분표를 촬영·등록하고 서로 공유하는 구조

**핵심 차별점**: 성분 입력을 "자판 타이핑"이 아니라 "사진 촬영 → 자동 인식 → 터치 편집"으로 최소화

## 2. 서비스 운영 범위 (v1.0)

- 회원가입 기능 없이, 운영자가 발급한 **임시 ID/PW**를 가진 초대된 테스터만 이용하는 **비공개 베타**
- 목적: 불특정 다수 접근을 차단해 스팸/오남용 리스크를 원천 차단하고, 초기 단계엔 사용성 검증에 집중

## 3. MVP 기능 (1.0)

### 3.1 사료 등록

- **성분표 사진은 앞면(제품명이 보이는 봉투 전면)·뒷면(성분표) 2장 촬영** (모바일 브라우저 카메라 input 지원)
- 업로드 전 클라이언트에서 이미지 리사이즈/압축, HEIC → JPEG 변환
- 촬영 가이드(사각 프레임)로 사진 품질 확보, 서버에서 대비 강화 등 전처리 후 OCR 수행 (OCR은 뒷면 성분표 사진 대상)
- **OCR: Tesseract.js** — 별도 서버 없이 Next.js 서버 프로세스 안에서 직접 실행 (v1.7까지는 PaddleOCR을 Render에 별도 배치하는 방향이었으나, 실제 구현 중 무료 티어(RAM 512MB) 대비 PaddleOCR 최소 실행 메모리가 실측 ~600MB로 초과해 계속 크래시함을 확인 — 로컬에서 파이프라인 단계별 메모리를 직접 측정해 확정. 한국어 인식률은 PaddleOCR보다 낮지만, OCR은 실패해도 등록을 막지 않는 보조 기능이라 감내 가능하다고 판단)
- 자체 파싱 로직으로 OCR 텍스트 → 성분 태그 후보 매칭
- **성분 태그는 자유 입력이 아니라, 사전에 등록해둔 "제공 태그 목록" 안에서만 선택** (자유 입력 시 발생하는 중복·오타로 인한 데이터 품질 저하 방지)
- **태그 후보는 세 가지 상태로 구분**:
  - **매칭됨(확정)**: 파싱 로직이 DB 성분과 성공적으로 매칭
  - **미해결**: OCR은 텍스트를 뽑았지만 DB 성분과 매칭되지 않은 상태 — 아직 아무 조치도 안 한 상태
  - **요청됨(검토중)**: 사용자가 검색해도 DB에 없어 "추가 요청하기"로 처리한 상태
- 미해결 태그를 탭하면 검색 화면이 열리고, 해당 키워드가 검색어로 미리 채워진 채 DB 성분을 검색해 매칭할 수 있음. 검색 결과가 없으면 그 자리에서 "추가 요청하기" 가능
- **"추가 요청하기"는 즉시 `ingredients`에 `status: pending`인 행을 생성하고 해당 제품에 바로 연결** — 운영자 승인을 기다리지 않고도 등록이 완결됨. 승인 전에도 검색·필터에 정상 노출되고 "검토중" 표시만 붙음. 다른 사용자가 같은 성분을 찾을 때도 이 pending 성분이 후보로 함께 노출되어 중복 요청을 방지
- **미해결 상태가 하나라도 남아있으면 다음 단계(제출)로 진행 불가.** 요청됨 상태는 정상 처리된 것으로 간주해 제출을 막지 않음
- OCR 인식 실패 시 두 가지 복구 경로: **"다시 촬영하기"**(뒷면 재촬영으로 복귀) 또는 **"태그 없이 계속하기"**(태그가 모두 비어있는 상태로 3단계 진입, 사용자가 전부 수동 검색으로 채움)
- 제품명/브랜드/사진 등 기본 정보 입력
- 등록 완료 (Create) — 최초 등록자는 로그인된 테스터 ID로 **서버가 자동 기록** (클라이언트가 임의 지정 불가)

### 3.2 사료 조회

- 제품 목록 보기
- 제품 상세 페이지 (성분 리스트, 등록 사진, 리뷰 표시)
- **신뢰 메타데이터 노출**: 등록자·최종 수정자(로그인 ID를 표시명으로 그대로 사용, 별도 사용자 테이블 불필요), 최종 수정일, **조회수**, **수정 횟수**
- **안전성 미검증 면책 문구 하단 노출** (제품 상세·리뷰 빈 상태 화면. 정확한 문구는 10.3 참고)
- 이름/브랜드/성분 기준 검색 (PostgreSQL `pg_trgm` 확장 기반)

### 3.3 사료 정보 수정 — 공유 데이터로 취급 (삭제 없음)

제품 정보(성분표 등)는 특정 사용자 개인 소유가 아니라 **모두가 같이 보는 공유 데이터**로 간주합니다. 제조사가 레시피를 바꾸거나 등록 당시 오탈자가 있었을 때, 최초 등록자가 아니어도 바로잡을 수 있어야 하기 때문입니다.

- **로그인한 테스터라면 누구나 제품 정보를 수정 가능** (등록자 본인이 아니어도 됨) — 위키형 공동 편집
- **v1.0에는 삭제 기능을 제공하지 않음.** 잘못 등록된 정보는 "삭제"가 아니라 "수정"으로 바로잡음 (삭제는 되돌릴 수 없는 데이터 유실로 이어지므로 의도적으로 제외)
- 모든 수정 시 `updated_at`, `updated_by`(마지막 수정 테스터)가 자동 갱신되고, 별도의 **변경 이력 로그**(`product_edit_logs`)에 "누가/언제/무엇을 바꿨는지" 기록 — 잘못된 수정이 발생해도 추적하여 수동으로 되돌릴 수 있게 함. 제품 상세의 "수정 횟수"는 이 로그의 건수를 그대로 노출(별도 카운터 필드 없이 파생값으로 계산 — 두 값이 어긋날 일이 없도록)
- 삭제가 정말 필요한 경우(중복 등록, 스팸 등)는 DB에서 운영자가 직접 처리 (UI에는 노출하지 않음)

### 3.4 리뷰

리뷰는 제품 정보와 달리 **작성자 개인의 의견**이므로 기존과 동일하게 소유권 기반으로 관리합니다.

- 제품별 리뷰 작성 (별점 + 텍스트) — **별점 미선택 시 제출 불가**, 에러 문구와 함께 버튼 비활성 표시
- 리뷰 목록 조회 (작성일 노출)
- **본인 리뷰만 수정/삭제 가능** — 서버가 로그인 세션 쿠키의 테스터 ID와 DB상 작성자를 대조해 검증

### 3.5 데이터 모델 (핵심 CRUD 대상)

- `products` (제품): 이름, 브랜드, 사진(앞면·뒷면), created_by(최초 등록자), **created_at, updated_at, updated_by**(마지막 수정 테스터), **view_count**(조회수, 상세 페이지 조회 시마다 증가)
- `ingredients` (성분 마스터): 성분명, **status**(`approved` 기본값 / `pending` — 사용자 "추가 요청"으로 생성된 미승인 성분) — 운영자가 사전 등록하거나 사용자 요청으로 생성되며, 사용자는 이 목록(pending 포함) 내에서만 선택
- `product_ingredients` (다대다 연결): product_id, ingredient_id
- `product_edit_logs` (변경 이력): product_id, editor(테스터 ID), edited_at, 변경 요약 — "수정 횟수" 표시의 근거 데이터이기도 함
- `reviews` (리뷰): product_id, user_id, 별점, 텍스트, created_at, updated_at

※ 안전성 판단(이 성분이 위험한지 여부)은 MVP 범위에서 제외. 순수 등록/검색/리뷰 CRUD에 집중.

## 4. 베타 접근 제어

- 회원가입 없는 비공개 베타: 운영자가 발급한 소수의 테스터 ID/PW로만 로그인
- 로그인 성공 시 서버가 **서명된 세션 쿠키(httpOnly)** 발급 — 브라우저 JS로 값 열람/조작 불가
- Next.js `middleware`가 세션 쿠키 없는 요청은 사이트 진입 자체를 차단 (로그인 페이지로 리다이렉트)
- **세션 만료 시 어느 화면에서든 자동으로 로그인 화면으로 전환** (만료 안내 배지와 함께), 클라이언트에서 세션 만료를 감지하는 처리 필요
- **로그아웃**: 헤더의 프로필 아이콘 → 드롭다운 메뉴("계정 정보" / "로그아웃") → 로그아웃 시 로컬 세션 정리 후 로그인 화면 이동
- 모든 쓰기 요청(등록/수정/리뷰)은 **Next.js Route Handler를 거쳐 서버에서만 Supabase에 접근**
- Supabase **service role key는 서버 환경변수로만 존재**, 브라우저 번들에는 절대 포함하지 않음
- 권한 검증 기준: **제품 정보 수정** — 로그인한 테스터인지만 확인(누구나 가능) / **리뷰 수정·삭제** — 세션 쿠키의 테스터 ID와 작성자 일치 여부까지 확인
- 제품 수정 시 세션 쿠키의 테스터 ID를 `updated_by`로 자동 기록, `product_edit_logs`에 로그 적재

## 5. 차후 업데이트 (2.0 이후)

- 로그인/인증: Supabase Auth 도입 (베타 로그인 구조를 그대로 확장, 기존 테스터 ID → 실 사용자 ID 매핑)
- 검색 고도화: 한국어 형태소분석 기반 전문검색(Full Text Search)으로 업그레이드 검토
- **브랜드 별칭(alias) 매핑**: 같은 브랜드를 영문("Dr.Clauder's")과 한글("닥터클라우더")로 다르게 등록해 검색이 서로 안 걸리는 문제 — `pg_trgm` 유사도로는 문자 체계가 달라 못 잡음(형태소분석 이슈와는 다른 별개 문제). `brand_aliases` 테이블 신설 + 등록 시 브랜드도 성분 태그처럼 기존 목록에서 검색·선택하게 바꾸는 방향 검토
- Rate limiting 도입 검토 (Upstash 등) — 오남용/오류로 인한 과다 요청 방지
- 성분 태그 목록을 「사료등의 기준 및 규격」/AAFCO 기준으로 정식 매핑·확장
- OCR 정확도 개선: Tesseract.js 인식률이 부족할 경우 PaddleOCR(유료 인스턴스로 재배치) 또는 Naver Clova OCR 등으로 교체 검토
- 검색 결과 필터: 특정 성분 포함/제외 등으로 필터링 — UI는 검색바 아래 고정 영역에 "N건 찾았어요" 옆 필터 아이콘 자리를 미리 마련해둠(`app/(main)/search/page.tsx`)
- 즐겨찾기/찜 기능
- 리뷰 "도움돼요" 반응(좋아요) 기능: 디자인 시안엔 있으나 8단계 구현 범위에선 제외 — 반응 저장용 테이블(누가 어떤 리뷰에 반응했는지) 신설 필요
- 알러지 성분 알림: 내 반려동물의 알러지 성분 등록 후 해당 성분 포함 사료 경고
- 마이페이지: 내가 등록한 제품, 내가 쓴 리뷰 모아보기
- 제품 비교 기능: 두 개 이상 사료 성분 나란히 비교
- 제품 정보 변경 이력을 사용자에게도 노출(예: "수정 내역 보기") 및 특정 시점으로 되돌리기(rollback) 기능 검토
- 제품 사진 재업로드/수정: 현재는 공유 데이터 원칙에 따라 수정 화면에서 이름·브랜드·성분만 고칠 수 있고 사진은 최초 등록 상태로 고정 — 아무나 수정 가능한 구조라 사진까지 열면 남용 위험이 있어 v1.0은 제외. 필요 시 변경 이력 노출/rollback과 함께 검토
- 사용자 신고 후 운영자가 승인하는 정식 삭제/병합(중복 제품 합치기) 플로우 도입
- **단종 신고**: 제품 상세 화면 우측 상단에 신고/제보 아이콘 — 지도 앱의 "폐업 신고"처럼, 사용자가 이 제품이 단종됐다고 표시하면 운영자가 확인 후 삭제 등 처리
- **부정확한 수정/등록 신고**: 의미 없는 정보를 일부러 올리거나 잘못된 내용으로 고치는 사용자를 신고하는 기능. 운영자가 확인 후 해당 테스터의 등록/수정 권한을 제한하는 방식 검토
- pending 성분에 대한 운영자 승인 화면(승인/거절/기존 성분과 병합) 도입 — v1.0은 DB 직접 처리로 대응
- 면책 문구를 제품 상세·리뷰 빈 상태 외 다른 데이터 노출 화면(검색 결과, 수정 화면 등)에도 확대 적용할지 검토

## 6. 기술 스택

| 영역 | 선택 | 비고 |
|---|---|---|
| 프레임워크 | Next.js (App Router) + TypeScript | |
| 스타일링 | Tailwind CSS | 디자인 토큰은 10번 참고, `tailwind.config`에 반영 |
| UI 컴포넌트 | shadcn/ui | CRUD 폼/다이얼로그 빠르게 구성 |
| DB | Supabase (Postgres) | 이미지 저장(Storage), Route Handler 경유로만 접근 |
| ORM (선택) | Prisma | 다대다 관계 스키마 관리, 생략하고 Supabase client로만 가도 무방 |
| OCR | Tesseract.js | Next.js 서버 프로세스 안에서 직접 실행, 별도 호스팅 불필요·무료. PaddleOCR 대비 한국어 인식률은 낮음 |
| 검색 | PostgreSQL `pg_trgm` 확장 | 한국어에도 언어 무관하게 동작, 인덱스 가능. 제품 유사 후보 추천과 성분 태그 검색에 동일하게 재사용 |
| 베타 인증 | 자체 로그인(임시 ID/PW) + 서명 세션 쿠키 | 정식 Auth는 2.0에서 Supabase Auth로 전환 |
| 폼/검증 | react-hook-form + zod | |
| 배포 | Vercel (프론트/API, OCR 포함) | |

## 7. 성분 태그 마스터 데이터 소스

- 참고 자료: 「사료등의 기준 및 규격」(농림축산식품부 고시, law.go.kr 행정규칙), 농림축산검역본부(QIA) 정보공개자료, 국제 참고자료로 AAFCO(미국 사료검사관협회) 성분 정의
- **주의**: 반려동물 사료는 사람 식품첨가물(식약처 관할)과는 별도의 규정 체계(농림축산식품부/QIA 관할)이므로 데이터 출처를 혼동하지 않도록 함
- **초기 전략**: 정식 공정서 전체를 미리 파싱하지 않고, 실제 사료 라벨 기준 자주 쓰이는 성분 100~200개를 수동 큐레이션하여 태그 목록을 시작
- **확장 경로**: 사용자가 등록 중 "추가 요청하기"로 만든 pending 성분들이 곧 목록 확장 신호가 됨 — 별도로 사용자 피드백을 취합할 필요 없이 운영자가 pending 목록을 주기적으로 검토·승인하면 됨. 여유 있을 때 정식 목록(「사료등의 기준 및 규격」/AAFCO)으로 매핑
- 서비스 시연 시 빈 화면 방지를 위해 더미 사료 데이터 시드(seed) 준비 필요
- 브랜드/성분 마스터 데이터 일부 미리 입력해두는 것 권장

## 8. 리스크 및 결정 사항 요약

- OCR(Tesseract.js) 인식률이 낮을 수 있음 → 사용자 터치 편집으로 보정하는 구조라 완벽한 정확도는 불필요. 인식 완전 실패 시에도 "태그 없이 계속하기"로 등록 자체는 막히지 않음
- 비공개 베타(임시 ID/PW) + 서버 프록시 구조(Route Handler + service role key 서버 전용)로, 인증 시스템 없이도 쓰기 권한 오남용 리스크를 최소화
- 성분 태그는 자유 입력이 아닌 **제공 목록 내 선택 방식**으로 운영해 데이터 품질(중복/오타) 관리
- **제품 정보는 공유 데이터로 간주해 등록자 외 테스터도 수정 가능하도록 개방하되, 삭제 기능은 v1.0에서 아예 제공하지 않음** (오등록/오수정은 재수정으로 대응, 진짜 삭제가 필요하면 운영자가 DB에서 직접 처리)
- 모든 제품 수정 내역은 `product_edit_logs`에 최소한으로 기록해, 잘못된 수정이 생겨도 누가/언제 바꿨는지 추적해 되돌릴 수 있게 함 — 이 로그가 "수정 횟수" 신뢰 지표로도 재사용됨
- 리뷰는 개인 콘텐츠이므로 제품 정보와 달리 본인만 수정/삭제 가능한 기존 원칙 유지
- **성분 태그가 DB에 없을 때는 "추가 요청하기"로 즉시 pending 성분을 만들어 제품에 바로 연결** — 운영자 승인을 기다리며 등록이 막히지 않으면서도, 아직 아무 조치 안 한 "미해결" 상태만은 제출을 막아 데이터 누락을 방지
- 성분 안전성 판단 로직은 의도적으로 MVP에서 제외 (범위 관리)
- **등록 정보는 사용자 입력 기반 참고용 데이터이며, 제품 상세·리뷰 빈 상태 화면 하단에 면책 문구 상시 노출** (정확한 문구는 10.3 참고)
- **등록자·최종 수정자·조회수·수정 횟수를 상세 화면에 노출** — 공유 데이터의 신뢰도를 사용자가 스스로 판단할 수 있게 하는 핵심 장치로, 데이터 모델(3.5)에 반드시 포함

## 9. 화면 구성 및 사용자 플로우

### 9.1 화면 목록

1. 로그인 (베타 게이트) — ID/PW 입력, 실패 시 에러 상태
2. **홈 (검색)** — 진입 시 첫 화면. 검색창이 중심
   - 2-1. 세션 만료 — 자동 전환, 로그인 폼 재사용
   - 2-2. 프로필/로그아웃 메뉴 — 헤더 프로필 아이콘 드롭다운
3. 검색 결과 (일치 없음 → 유사 후보 → 등록 유도 / 일치 있음 → 리스트)
4. 제품 상세 — 신뢰 메타데이터(등록자·수정자·조회수·수정횟수) + 하단 면책 문구 상시 노출(10.3)
   - 4-1. 리뷰 더보기
   - 4-2. 리뷰 빈 상태 — 면책 문구도 동일 노출
5. 성분표 등록 (다단계: 촬영(앞면→뒷면) → OCR 처리 중/실패 → 성분 태그 확인/편집 → 기본정보 입력 → 완료)
6. 제품 정보 수정 (등록 폼과 동일한 형태 재사용, 기존 값 프리필)
7. 리뷰 작성/수정 — 별점 미선택 검증 에러 상태 포함
8. 성분 태그 검색 (등록/수정 화면에서 태그 칩을 탭하면 열리는 서브 화면)
9. 공통 네트워크/서버 에러 — 모든 화면에서 재사용 가능한 전역 에러 컴포넌트

### 9.2 홈 화면 — 검색이 먼저, 등록은 그다음

- 앱 진입 시 첫 화면은 목록이 아니라 **검색창**. 초기엔 등록된 데이터가 적어 "둘러보기"보다 "이 제품이 있는지 확인"이 우선 행동이라는 판단
- **등록(성분표 촬영) 버튼은 검색창보다 아래, 화면 하단에 고정 배치** — 검색이 주 행동, 등록은 보조 행동이라는 위계를 화면 배치로 표현

### 9.3 검색 → 결과 없음 → 등록 유도 플로우

1. 검색어 입력 → 검색 실행
2. **정확히 일치하는 결과가 있으면** → 목록으로 바로 표시
3. **정확히 일치하는 결과가 없으면** → "혹시 이런 제품을 찾으셨나요?" 문구와 함께 **유사 후보**(제품명/브랜드 유사도 기준) 카드 목록 노출
   - 검색 방식으로 정한 `pg_trgm`이 오타·부분 일치 기반 유사 후보 추천에 그대로 재사용됨 (별도 기능 추가 없이 동일한 검색 인덱스 활용)
4. **후보 중에도 원하는 제품이 없으면** → "찾는 제품이 없나요? 직접 등록해보세요" 안내 문구와 함께 등록 화면으로 이동하는 버튼 노출
   - 유사 후보가 아예 0건이면 3번을 생략하고 바로 4번으로
   - 등록 화면 진입 시 검색어를 제품명 입력란에 미리 채워두면(prefill) 사용자가 다시 타이핑하지 않아도 됨 (구현 시 고려)

### 9.4 등록 플로우 (다단계)

1. **사진 촬영 — 앞면(제품명이 보이는 봉투 전면)**, 이어서 **뒷면(성분표)** 순서로 2장 (카메라 가이드 프레임 노출)
2. OCR 처리 중 — 로딩 상태 (수 초 소요될 수 있음을 알려주는 안내 문구 필요). 인식 실패 시 **"다시 촬영하기"**(뒷면 재촬영) 또는 **"태그 없이 계속하기"**(태그 빈 상태로 3단계 진입) 두 경로 제공
3. **성분 태그 확인/편집** — OCR로 뽑은 후보를 매칭됨/미해결/요청됨 세 상태의 칩으로 표시
   - 매칭됨: 확정 스타일
   - 미해결(회색): 아직 조치 안 함 — 탭하면 해당 키워드가 프리필된 **성분 태그 검색 화면**(9.6)이 열림
   - 요청됨(검토중): 사용자가 추가 요청 완료한 상태 — 점선 테두리 등으로 구분, 다시 탭하면 실제 성분으로 교체 가능
   - **미해결 태그가 하나라도 남아있으면 다음 단계 버튼 비활성화**, "아직 확인이 필요한 성분이 있어요" 안내 노출. 요청됨 상태는 제출을 막지 않음
4. 기본정보 입력 — 제품명(검색에서 넘어온 경우 프리필), 브랜드, "등록하면 모두가 함께 보는 공유 데이터가 돼요" 안내 문구
5. 등록 완료 → 첫 등록자에게는 "OO님이 첫 등록자예요" 인정 메시지 → 방금 등록한 제품의 상세 화면으로 이동

### 9.5 예외/빈 상태

- OCR 인식 실패·저품질 → 성분 태그 후보 없이도 수동 선택만으로 등록을 계속 진행할 수 있어야 함 ("태그 없이 계속하기")
- 검색 결과 0건 + 유사 후보도 0건 → 9.3의 3번을 건너뛰고 바로 4번(등록 유도)으로
- 등록 3단계에서 미해결 태그가 남은 채로 다음 단계 진입 시도 → 제출 버튼 비활성화 + 안내 배너, 미해결 태그 강조 표시
- 성분 태그 검색 결과 0건 → "추가 요청하기" 노출, 요청 시 즉시 pending 성분으로 생성되어 제품에 연결됨(칩은 "요청됨"으로 전환)
- 리뷰 작성 시 별점 미선택 → 에러 문구 노출, 제출 버튼 비활성 스타일
- **API/네트워크 요청 실패 (공통)** → 전역 에러 화면/컴포넌트로 처리, "다시 시도" 시 직전 요청 재시도

### 9.6 성분 태그 검색 화면 (등록/수정 중 태그 칩을 탭하면 열림)

- 검색창이 중심. 미해결(회색) 키워드를 탭해서 들어온 경우, 그 키워드 텍스트가 검색창에 자동으로 채워짐
- 타이핑하면 `pg_trgm` 기반으로 관련 성분 후보가 실시간으로 표시 (approved/pending 성분 모두 후보에 포함, pending은 "검토중" 배지로 구분)
- 후보 선택 시 화면이 닫히고 원래 화면의 해당 칩이 선택한 성분으로 갱신(매칭됨 상태로 전환)
- 검색 결과 0건 → "이 성분 추가 요청하기" 버튼 노출 → 요청 시 pending 성분 생성 및 즉시 연결, 화면이 닫히며 원래 칩이 "요청됨" 상태로 전환
- 카테고리별 탐색 UI는 v1.0 범위에서 제외 — 검색이 항상 더 빠르다는 판단. 대신 자주 쓰이는 성분 몇 개를 검색창 근처에 퀵 선택 칩으로 노출하는 정도는 고려 가능

### 10.3 면책 문구 (최종)

**제품 상세·리뷰 빈 상태 화면 하단 상시 노출**:

> "이 정보는 사용자들이 함께 등록·수정한 내용으로, 성분의 안전성이 검증된 것은 아니에요. 반려동물 건강에 관한 결정은 수의사와 상의해주세요."

(디자인 핸드오프 문구로 최종화 — 기존 합쇼체 초안보다 서비스의 귀여운 톤과 더 자연스럽게 맞음). 다른 데이터 노출 화면(검색 결과, 수정 화면 등)으로 확대 적용할지는 5번 "차후 업데이트"에 열린 과제로 남김.

등록 폼 쪽 안내("등록하면 모두가 함께 보는 공유 데이터가 돼요 · 등록 후에는 임의로 지울 수 없고, 잘못된 내용은 수정으로 바로잡아요")는 이미 시안에 반영되어 있어 별도 문구 추가가 필요 없음 — 이 문구는 "정보가 검증되지 않았다"는 것과는 다른 이야기(공유 편집 구조 안내)이므로 그대로 유지.
